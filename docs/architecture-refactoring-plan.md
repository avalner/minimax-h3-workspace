# План архитектурного рефакторинга для агента

Дата: 12 ноября 2026 года.

## Задание и ожидаемый результат

Провести постепенный рефакторинг Minimax H3 Workspace: обеспечить восстановление заданий и результатов после сбоя, централизовать управление фоновыми задачами, отделить прикладную логику от HTTP и разделить интерфейс на модули. Сохранить существующие пользовательские сценарии, рецепты графов и публичные контракты.

Это исполнимый план, а не разрешение переписать приложение целиком. Работать последовательно; после каждого этапа приложение должно запускаться. Перед изменениями прочитать актуальные AGENTS.md, если они появились, проверить состояние Git и сохранить чужие изменения. Номера строк исходного анализа могут измениться; ориентироваться на имена функций.

Результат работы: изменения кода, миграции существующих данных, проверки сценариев отказа, обновлённая документация и отчёт о выполнении каждого этапа. Если проверку нельзя выполнить в доступном окружении, указать это явно, привести команду и не считать её пройденной.

## 1. Контекст и места для начала работы

| Область | Текущие точки входа | Основная проблема |
| --- | --- | --- |
| Задания | `app/server.py`: JobStore, queue, finish_job, on_comfy_event, reconcile_jobs, jobs_watchdog | Мутации словарей заменяют явные переходы состояния; результат сохраняется после удаления задания |
| Восстановление | load_queue, save_queue, h_queue_resume, h_queue_discard | Очередь очищается до завершения восстановления; живые задания пропускаются без повторной регистрации |
| Хранение | engine.Config, Library, QUEUE_FILE, LONG_DIR, WORKFLOWS_DIR | Разные правила записи, отсутствует общая версия схемы |
| Результаты | hold_preview, h_preview_keep, archive_item, file_path, run_ffmpeg_job, poll_cloud | Разные способы финализации; нет единого протокола записи файла и метаданных |
| Фоновые операции | App.start, App.stop, create_task, _bg, installer, ffmpeg_jobs | Неполный учёт задач и завершение без ожидания отмены |
| Внешний API | app/agentapi.py: создание видео, job_view, _remember_key | Доступ к внутренностям App, разбор HTTP-ответа общей операции, idempotency только в памяти |
| Окно | app/main.py: ServerThread.run, shutdown | Ошибки старта и завершение loop необходимо согласовать с сервером |
| Интерфейс | app/ui/index.html: connectEvents, previewPanel, восстановление параметров | Общий большой скрипт; выбор модели восстанавливается из подписи meta.sub |
| Сборка | run.bat, app/start.bat, app/build/h3studio.spec | Невоспроизводимые зависимости; новые JS/CSS-файлы нужно включить в exe |

Уточнение исходного анализа: наследование JobStore от dict само по себе не гарантирует сохранение вложенных изменений `job[...]`. Не пытаться расширять этот механизм перехватом всех мутаций. Перейти к явным операциям сервиса и репозитория.

## 2. Обязательные ограничения

- Все автоматические проверки работают с временным H3STUDIO_DATA, отдельным H3STUDIO_AGENT_FILE и поддельными backend. Не использовать пользовательскую библиотеку или рабочий ComfyUI в тестах.
- Сохранить loopback-привязку сервера, middleware проверки origin, авторизацию агентов, ограничения путей входных файлов и Windows Job Object.
- Сохранить маршруты UI, /api/agent/v1, формат обнаружения agent.json и MCP-инструменты. Внутренние состояния переводить в существующий контракт адаптерами.
- Черновик не становится библиотечным результатом без действия пользователя. Автоматическое сохранение результата агентского задания в библиотеку сохраняется.
- Не менять самовольно срок жизни черновиков: сейчас pending находится в памяти и имеет лимит. До изменения зафиксировать точную текущую семантику. Долговечное восстановление заданий не должно автоматически означать долговечное восстановление всех черновиков в UI.
- Не менять рецепты генерации, веса LoRA, размеры, seed и настройки моделей при структурном рефакторинге.
- Не вводить микросервисы, брокер сообщений, ORM или сборщик фронтенда без конкретной необходимости. SQLite доступен в стандартной библиотеке; ES modules подходят для первого разделения UI.
- Не обещать exactly-once отправку во внешний backend: локальная БД и удалённый POST не образуют общей транзакции.
- Не удалять исходные JSON и резервные копии при первой успешной миграции. Не выполнять разрушительные действия с пользовательскими файлами для проверки восстановления.

## 3. Целевая структура и правила зависимостей

Ориентир, допускается адаптация имён к существующим импортам и PyInstaller:

```text
app/
  main.py                 # окно, запуск и остановка сервера
  server.py               # сборка зависимостей и подключение маршрутов
  domain/
    jobs.py               # состояния, JobSpec, JobRecord, правила переходов
    media.py              # MediaRecord, ссылки на файлы, политика черновиков
    errors.py             # прикладные ошибки, без aiohttp
  services/
    jobs.py               # submit, reconcile, finalize, cancel, retry
    media.py              # регистрация результатов, архивирование, библиотека
    engines.py            # процессы, restart, GPU/LLM coordination
  storage/
    atomic.py             # атомарные JSON и маленькие файлы
    database.py           # соединение, транзакции, версия схемы
    repositories.py       # задания, результаты, ключи повторных запросов
    migrations.py         # импорт и обновления схемы
  backends/
    comfy.py              # протокол ComfyUI
    runninghub.py          # существующий cloud.py может остаться реализацией
    ffmpeg.py              # адаптер существующего ffmpeg_mgr.py
  runtime/
    tasks.py              # TaskSupervisor
    events.py             # уведомления и доставка WebSocket
  http/
    jobs.py, media.py, ... # группы маршрутов, тонкие обработчики
  ui/
    index.html
    css/...
    js/api.js, events.js, state.js, components/..., modes/...
```

Направление зависимостей: HTTP → services → domain и интерфейсы storage/backends. Конкретные реализации соединяются в build_app. Domain не импортирует server, aiohttp, pywebview или subprocess. Backend не получает весь App. Не создавать пустые слои и классы только ради схемы: переносить ответственность вместе с её реальным использованием.

## 4. Порядок реализации

### Этап 0. Зафиксировать поведение и окружение

1. Найти рабочий Python 3.10+ и записать фактические версии зависимостей. Проверить оба .bat и spec сборки. Не устанавливать пакеты в ComfyUI пользователя.
2. Запустить имеющиеся проверки: video_fused_graph_test.py, gpu_watchdog_test.py, agent_api_smoke.py. MCP smoke запускать с отдельным тестовым экземпляром приложения; не запускать --render без явного запроса на реальную генерацию.
3. Составить таблицу HTTP/WebSocket-контрактов, мест изменения jobs/pending/library/recent/history, всех create_task и потоковых callback. Зафиксировать настройки отмены и перезапуска внешнего ComfyUI.
4. Сохранить тестовые примеры старых config.json, queue.json, library.json, результатов и проекта длинного видео. Использовать синтетические данные без токенов и пользовательских промптов.
5. Добавить минимальный общий test runner и отдельные зависимости разработки. Зафиксировать проверенные зависимости приложения и сборки; документировать обновление. Не закреплять случайные версии без проверки запуска.

Приёмка: есть повторяемая команда проверок, таблица исходного поведения и явно перечисленные недоступные проверки. На момент составления плана команда python в текущей сессии указывала на Windows Store alias; успешный запуск тестов пока не подтверждён.

### Этап 1. Закрыть непосредственные риски потери данных

Это небольшой самостоятельный набор исправлений до крупного переноса модулей.

1. Реализовать общий atomic_write: уникальный временный файл рядом с целевым, полная запись, flush/fsync там, где применимо, os.replace, очистка временного файла при ошибке. Учитывать Windows file locking. Не заявлять абсолютную защиту от отказа оборудования.
2. Применить его к Config.update, save_queue и Library.save; затем к небольшим JSON состояния сцен, проектов, workflow и чатов по карте записей из этапа 0. При ошибке не оставлять память в состоянии «успешно сохранено», если запись не состоялась.
3. Ошибки обязательного сохранения логировать с контекстом и сообщать вызывающему коду. Фоновая ошибка не должна создавать ложный успех в UI.
4. В finish_job не удалять задание до регистрации результата. Ввести временное состояние finalizing и защиту от повторной финализации; учесть finish_job из WebSocket, reconcile и отмены.
5. В h_queue_resume не очищать всю saved_queue заранее. Завершать восстановление каждого элемента отдельно. Живое задание присоединять к наблюдению; завершённое искать в history; недоступный backend не считать пустой очередью.
6. В h_preview_keep не терять pending-запись при ошибке сохранения в библиотеку; повторное сохранение должно возвращать тот же результат.

Приёмка: сбой записи сохраняет читаемую предыдущую версию; отказ одного элемента восстановления не теряет остальные; повторный execution_success не создаёт дубликат; между генерацией и регистрацией результата задание остаётся обнаруживаемым.

### Этап 2. Ввести модели и единый протокол задания

1. Добавить типизированные JobSpec, JobRecord, MediaRecord и ошибки сервиса. Использовать dataclass/Enum и явную валидацию; тяжёлая библиотека для этого не обязательна.
2. Хранить отдельно: стабильный внутренний job_id, backend, backend instance/endpoint identity, backend_job_id, режим, schema_version, исходные и вычисленные параметры, граф, seed, входные файлы, политика результата, timestamps, ошибка и ссылки на результаты.
3. Существующий prompt_id оставить совместимым публичным идентификатором. Не переименовывать публичные поля и не менять ссылки старых записей. Явно описать сопоставление internal ID, prompt_id и backend_job_id.
4. Определить переходы: created → submitting → queued → running → finalizing → succeeded. Отмена оформляется запросом и подтверждённым исходом; finalizing после подтверждённой генерации не отменять как выполняющийся GPU job.
5. Предусмотреть failed, canceled и состояние неопределённой отправки/необходимости сверки. Временно недоступный backend не равен failed. Ошибка скачивания результата допускает повтор финализации без повторной генерации.
6. Вынести model_variant, acceleration, model/LoRA snapshot, backend, параметры размеров и preview policy в данные. sub остаётся отображаемой подписью.
7. Переходы выполнять через единый метод с проверкой текущего состояния и версии записи. Терминальные исходы не переопределяются запоздалым событием. Прогресс хранить отдельно и не записывать в БД на каждый шаг без необходимости.

Приёмка: правила переходов проверяются без aiohttp и GPU; сериализация имеет версию; одинаковый JobSpec даёт одинаковые параметры независимо от источника UI/API; допустимая разница политик результата задана явно.

### Этап 3. Ввести долговечное хранилище и миграцию

1. Создать SQLite в каталоге H3STUDIO_DATA. Отдельные таблицы: schema_migrations, jobs, media, job_results, idempotency_keys. Большие графы и специфичные параметры допустимо хранить как версионированный JSON в записи.
2. Добавить уникальность результата по job + backend output identity, индексы активных заданий и поиска результатов, foreign keys. Для уникальности учитывать node/subfolder/type/filename, а не только имя файла.
3. Определить модель конкурентного доступа: один сериализованный DB worker либо отдельные соединения с короткими транзакциями. Не передавать одно sqlite-соединение в произвольные to_thread. Не блокировать event loop ожиданием DB lock.
4. Настроить timeout блокировок, режим journal и durability под выбранную модель. Учесть, что после WAL появляются сопутствующие файлы: перенос DATA_DIR через datadir.py и резервное копирование должны выполняться после корректного закрытия БД либо средствами backup API.
5. Импортировать библиотеку с сохранением id, путей, избранного и неизвестных полей; очередь — без автоматической отправки; связанные метаданные — без выдумывания утраченных параметров.
6. Миграцию выполнять транзакционно и идемпотентно с резервной копией и маркером версии. Повторный старт не импортирует старый JSON заново. Повреждённые записи сохранять для диагностики; не заменять библиотеку пустым списком молча.
7. После переключения SQLite становится единственным источником истины для перенесённых сущностей. Не оставлять бессрочную двустороннюю запись JSON/SQLite. Конфигурация и проекты могут остаться атомарными JSON.
8. Описать восстановление из резервной копии и ограничения запуска старой версии приложения после миграции. Будущую неизвестную версию схемы открывать с понятной ошибкой без её перезаписи.

Приёмка: импорт старой библиотеки и очереди проходит повторно без дублей; прерванная миграция не оставляет частично переключённое хранилище; перемещение каталога данных не теряет транзакции; ошибки диска и блокировки видимы.

### Этап 4. Выделить JobService и backend-адаптеры

1. Начать с вертикального сценария video: HTTP parser → JobSpec → JobService → Comfy backend → repository. Затем подключать остальные режимы.
2. Перенести общую валидацию и выбор модели из UI/API обработчиков в общий путь подготовки. Проверки HTTP-формата остаются в HTTP. Не смешивать перенос кода с изменением рецептов workflows.py.
3. Реализовать submit, get_job, list_jobs, request_cancel, reconcile, finalize и явный retry. Возвращать DTO и ошибки сервиса, а не web.Response.
4. Задать небольшой backend-протокол: submit, inspect/reconcile, cancel, enumerate_outputs, download_output; capabilities отражает реальные возможности. FFmpeg не обязан изображать удалённую GPU-очередь.
5. Перед удалённой отправкой сохранить submitting. После ответа сохранить backend_job_id. На сбое между POST и записью ID искать подтверждённое задание по доступным метаданным backend; если доказательств нет, оставлять неопределённый исход, а не автоматически запускать повторно.
6. Восстановление сначала сверяет queue/history/status исходного backend. Нельзя отправлять незавершённое задание в другой сервер после изменения настроек пользователя.
7. Объединить результаты WebSocket, polling, watchdog и recovery в один идемпотентный путь переходов. Не держать общую DB-транзакцию или глобальный lock во время HTTP/копирования файлов.
8. Сделать idempotency_keys долговечными: атомарное резервирование ключа до первого await внешней операции, fingerprint нормализованного запроса, конфликт при другом payload, повтор с тем же payload возвращает существующее задание. Область ключей должна сохранить совместимость текущего API; client — пользовательский текст, а не доверенная identity.
9. Одновременные запросы одного ключа и повтор после рестарта не создают новые задания. При неопределённой отправке ответ честно описывает этот статус и не обещает безопасный повтор генерации.
10. Перенести отмену без потери текущих особенностей: отдельное queued/running/cloud/FFmpeg поведение, гонка отмены с успехом, локальность перезапуска, уведомление о других затронутых заданиях. Запрос отмены конкретного неизвестного ID не должен случайно останавливать чужую работу; существующую UI-команду «остановить текущее» оформить отдельной явной операцией с совместимым адаптером.

Приёмка: перезапуск приложения присоединяет живые задания и забирает готовые; повторные события безопасны; гонка cancel/success сохраняет подтверждённый результат; два запроса с одним ключом дают одно задание; неопределённый POST не повторяется автоматически.

### Этап 5. Унифицировать финализацию и файлы результатов

1. Ввести MediaService/Repository. Разделить сущности: результат backend, доступный файл, черновик, запись библиотеки, архивная копия. Успешная генерация не означает, что копия уже сохранена.
2. Общая финализация: зарегистрировать finalizing → найти и проверить outputs → подготовить необходимые файлы → транзакционно зарегистрировать результаты и succeeded → отправить уведомление.
3. Скачивать потоково в уникальный .part рядом с целевым файлом; проверять HTTP status, завершённость передачи и ожидаемый размер, если он известен; затем атомарно переименовывать. Для latent и видео не использовать r.read() целиком.
4. Большие локальные копии и сериализацию/операции с крупными файлами выполнять вне event loop. Отмена asyncio.to_thread не останавливает поток: использовать кооперативный cancel token, дождаться остановки writer до удаления .part.
5. Не пытаться объединить файловую систему и SQLite одной «атомарной» транзакцией. Сохранять этап финализации, стабильные назначения файлов и правила recovery для сбоев до/после rename и DB commit.
6. Архивирование учитывать отдельным статусом. Если источник остаётся доступен, ошибка дополнительной копии не должна требовать новой генерации; пользователь должен видеть, что независимая копия пока не создана.
7. Добавление черновика в библиотеку делать идемпотентным, сохранять item id. Не публиковать незавершённый файл как готовый. После рестарта применять согласованную политику черновиков и сохранения временных данных.
8. Очистку выполнять только для известных временных файлов, без активных writers и без ссылок из заданий/проектов/библиотеки. Не расширять текущую политику удаления оригиналов без отдельного решения.

Приёмка: сбой скачивания не оставляет готовый повреждённый mp4; повтор финализации не создаёт второй item; ошибка архивирования допускает повтор копирования; закрытие приложения во время записи не приводит к удалению файла активным cleanup; черновик не появляется в библиотеке автоматически.

### Этап 6. Централизовать фоновые задачи и управление процессами

1. Ввести TaskSupervisor со spawn(name, coroutine), хранением ссылок, обработкой исключений, запретом новых задач при shutdown и ограниченным ожиданием завершения.
2. Перевести под него Comfy WS, watchdog loops, cloud polling, установки, загрузки моделей/LoRA/FFmpeg, ожидание отмены, фоновые операции агента и FFmpeg. Для каждого типа описать завершение и владельца ресурса.
3. Последовательность shutdown: перестать принимать новые операции → остановить циклы и установщики → передать cancel токены потокам/процессам → дождаться writers и финализаторов в пределах общего бюджета → сохранить состояние восстановления → закрыть backend clients/HTTP → закрыть DB → завершить принадлежащие приложению процессы и loop.
4. Согласовать общий budget с ServerThread.shutdown: сейчас main.py ждёт cleanup до 30 секунд. Не позволять outer timeout оборвать внутреннюю запись без протокола восстановления. Соблюсти ограничения владения существующим внешним ComfyUI.
5. Выделить EngineManager: managed/external process, restart lock, coalescing параллельных restart, координация VRAM с LLM. Не менять пороги watchdog.py в этом переносе.
6. Учитывать, что shutdown приложения не равен cancel удалённого облачного задания. Сохранять его ID и возобновлять наблюдение после запуска.
7. В main.py передавать ошибку старта из ServerThread в окно/консоль; не открывать URL как успешно запущенный сервер после timeout. Закрывать loop и ожидать поток после cleanup.

Приёмка: нет обращений к закрытой сессии, необработанных Task exception и оставшихся управляемых child processes; два restart не запускают два ComfyUI; удалённый job переживает закрытие UI; незавершившаяся за budget операция имеет восстановимое состояние и диагностическую запись.

### Этап 7. Отделить HTTP и доставку событий

1. Перевести AgentAPI на JobService/MediaService. Удалить разбор response.text общей операции и прямое изменение внутренних App-словарей. Аналогично перенести UI API по группам маршрутов.
2. Ввести единое отображение прикладных ошибок в существующие HTTP-форматы. Уточнить различия статусов UI/API тестами контракта, без массового «выравнивания» публичного поведения.
3. Внутренние submitting/finalizing/recovering переводить в совместимые состояния /api/agent/v1 и WebSocket. Не превращать finalizing в 404 или ложное done.
4. Отвязать сохранение исхода от broadcast/remember: факты хранятся независимо от наличия браузеров. События отправляются после commit.
5. Медленный WebSocket-клиент не должен блокировать финализацию остальных заданий. Ввести ограниченные очереди отправки/timeout; прогресс можно объединять, терминальный статус всегда восстанавливается через snapshot/API.
6. После reconnect UI сначала синхронизирует состояние. Доставка WebSocket допускает повтор: потребитель обрабатывает событие идемпотентно. Durable event outbox вводить только при доказанной необходимости, не для замены доступного snapshot.

Приёмка: контрактные проверки старых маршрутов и MCP проходят; отключённый браузер не теряет исход задания; reconnect восстанавливает список и статусы; медленный клиент не задерживает DB commit и API.

### Этап 8. Исправить схему параметров и разделить UI

1. Сначала заменить восстановление модели через /fused turbo/i по meta.sub на явные параметры JobSpec. Для старых записей сделать один legacy normalizer; при неизвестных данных показывать ограничение, не утверждать точность восстановления.
2. Вынести api.js: проверка HTTP-статусов, парсинг ошибок, timeout/abort. Не добавлять автоматические повторы POST генерации без idempotency key.
3. Вынести events.js: одно соединение, backoff reconnect, регистрация/удаление подписок, resync; state.js: состояние заданий и результатов по ID. Не допускать нескольких владельцев одного состояния.
4. Вынести общие компоненты: previewPanel, media slots, параметры размеров/seed, LoRA controls. Затем переносить режимы по одному: video → images → refs/actor/swap → long → montage → настройки/агент.
5. Для каждого режима обеспечить mount/dispose или равнозначную очистку listeners, timers, subscriptions и object URLs. Сохранить localStorage keys, drag/drop, pywebview bridge и навигацию.
6. Вынести CSS по смысловым группам без изменения дизайна. На первом проходе не менять DOM-структуру и стили одновременно с переносом логики.
7. Обновить h3studio.spec: сейчас datas явно включает index.html и previews, а не весь новый UI. Проверить упаковку всех js/css и загрузку ES modules с правильным content type через локальный сервер.

Приёмка: смена подписи/языка не меняет восстановленную модель; многократная навигация не дублирует обработчики и отправки; основные сценарии одинаково работают в браузере и WebView2, из исходников и из собранного приложения.

### Этап 9. Завершить разделение и документацию

1. Удалить неиспользуемые JobStore, saved_queue и параллельные recent/history после переноса их ответственности. Временные adapters удалять только после переключения всех потребителей.

3. Оставить engine.py, cloud.py, ffmpeg_mgr.py и workflows.py там, где они уже выполняют узкую полезную роль; разделять дальше по реальным обязанностям. Не вводить общий DSL графов в рамках этого плана.
4. Добавить структурированную диагностику: job_id, backend_job_id, transition, операция, длительность и тип ошибки. Не писать токены, полное содержимое чувствительных запросов и секреты конфигурации в логи/отчёты.

Приёмка: domain/services не зависят от HTTP/window; бизнес-операции тестируются без создания App; новая установка и обновление со старыми данными проходят; весь план отмечен выполненным либо содержит конкретный остаток работ и причину.

## 5. Обязательные проверки отказов

Это проверки реальных границ состояния, а не тесты каждого перенесённого метода.

| Сценарий | Ожидаемый результат |
| --- | --- |
| Сбой записи конфигурации или очереди | Предыдущие данные читаемы; ошибка видима; память не заявляет несуществующее сохранение |
| Обрыв после POST /prompt до записи ID | Состояние неопределённой отправки; автоматического дублирующего POST нет |
| Потерян WebSocket после завершения генерации | reconcile забирает output из history, появляется один результат |
| Повторные success от WS и reconcile | Одна финализация и одна запись каждого результата |
| Рестарт во время finalizing | Возобновляется получение/регистрация результата без повторной генерации |
| Рестарт до/после rename, до/после DB commit | Восстановление либо завершает финализацию, либо оставляет диагностируемый retry; библиотека не ссылается на .part |
| Восстановление очереди с одним ошибочным элементом | Остальные задания сохраняются и восстанавливаются независимо |
| Backend временно недоступен при старте | Его задания не признаются пропавшими и не отправляются повторно |
| Сменился backend URL | Старое задание сверяется с исходным backend либо требует явного решения |
| Два одновременных запроса одного idempotency key | Один backend submit; оба получают один публичный ID |
| Тот же ключ, другой payload | Явный конфликт без нового submit |
| Повтор ключа после рестарта | Возвращается прежнее задание в пределах документированного срока хранения ключа |
| Cancel одновременно с success | Однозначный исход; подтверждённый output не теряется |
| Повтор «Добавить в библиотеку» | Тот же item, без дубликата и повторной ненужной копии |
| Ошибка диска при архивировании | Источник не удаляется; статус копии честный; доступен retry |
| Обрыв скачивания большого видео | Нет публикации неполного файла; память не растёт пропорционально размеру видео |
| Shutdown при активном thread writer | Writer остановлен/дождались; cleanup не соревнуется с ним за файл |
| Медленный/оборванный WebSocket клиент | Не тормозит фиксацию результата; после reconnect доступен актуальный snapshot |
| Повтор миграции и ошибка её середины | Нет дублей и частично переключённого хранилища |
| Перенос DATA_DIR с SQLite | База открывается, все подтверждённые записи и связи сохранены |
| Длительное переключение режимов UI | Не накапливаются timers/listeners/object URLs; нет повторных submit |

Использовать barriers/events для управляемых гонок, fake backend и инъекцию отказов I/O. Для проверки долговечности нужен хотя бы один интеграционный тест с аварийным завершением дочернего тестового процесса и повторным запуском на том же временном каталоге. Unit-тест исключения не заменяет проверку рестарта.

Реальные GPU/облачные генерации не являются обязательной автоматической проверкой рефакторинга. Если они недоступны, проверить сборку графов и протоколы fake backend и явно указать границу проверки.

## 6. Разбиение изменений и зависимости

Рекомендуемые отдельные ревьюируемые изменения:

1. Baseline, тестовое окружение, fixtures и воспроизводимые зависимости.
2. Атомарные записи и непосредственные исправления finish/resume/preview keep.
3. Типы заданий, схема параметров и правила переходов.
4. SQLite, repositories, миграции и backup/recovery.
5. JobService и Comfy backend для video; совместимые UI/API adapters.
6. Остальные режимы, долговечная idempotency, восстановление и отмена.
7. MediaService, потоковые файлы и повторяемая финализация всех backend.
8. TaskSupervisor, EngineManager и согласованный shutdown.
9. Группы HTTP-маршрутов и независимая доставка событий.
10. UI modules, явные параметры восстановления и обновлённая упаковка.
11. Удаление временных adapters, итоговые проверки и документация.

Изменения 3–7 тесно связаны: после каждого оставить рабочий совместимый путь, но не создавать два независимых источника состояния. Не начинать массовый перенос UI до стабилизации DTO и snapshot-контрактов. Исправление упаковки UI входит в тот же этап, что и вынос первого внешнего JS/CSS-файла.

## 7. Формат отчёта агента

После каждого этапа записать в рабочий журнал:

- выполненные пункты и затронутые контракты;
- точные команды и результаты проверок;
- изменения формата данных и порядок миграции/восстановления;
- оставшиеся ограничения и следующий этап.

Финальный отчёт должен отдельно подтвердить восстановление без потери/дублирования заданий, совместимость API/MCP, семантику черновиков, корректный shutdown и работу собранного приложения. Не отмечать весь рефакторинг завершённым по одному уменьшению server.py или успешным unit-тестам.
