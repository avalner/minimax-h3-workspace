# Этап 7. HTTP и доставка событий

Дата: 12 ноября 2026. План: [architecture-refactoring-plan.md](../architecture-refactoring-plan.md).
Предыдущий этап: [stage-6-report.md](stage-6-report.md).

Задача этапа — отделить доставку событий от фактов и от работы: исход задания сохраняется независимо
от того, открыто ли окно; медленное или замёрзшее окно не задерживает ни запись результата, ни
следующее задание; после переподключения окно сначала получает состояние, а не догоняет события.
Агентский API перестал быть вторым путём к тем же операциям: отмена и запуск возвращают данные
сервиса, а коды ошибок собраны в одну таблицу.

## 2. События: факт отдельно, доставка отдельно

До этапа `App.broadcast` по очереди ждал `ws.send_str` каждого окна. Замёрзшее окно (спящий ноутбук,
заблокированный WebSocket) задерживало конец финализации и все остальные окна — хотя запись в базе уже
была сделана.

Теперь [runtime/events.py](../../app/runtime/events.py):

- **факт — не событие.** `publish` сначала вызывает запись исхода (`App.remember`), потом ставит
  событие в очереди. Судьба задания не зависит от того, открыто ли окно: `recent`, запись Библиотеки
  и `media` пишутся своим порядком (этап 5 пишет их до уведомления).
- **события ставятся в очередь, а не отправляются.** У каждого окна свой ограниченный `asyncio.Queue`
  (256) и своя задача-отправитель под `TaskSupervisor`. `publish` не ждёт сокет, поэтому медленный
  клиент не задерживает ни финализацию, ни API.
- **прогресс можно терять, исход — нельзя.** При полной очереди событие прогресса отбрасывается (окно
  получит следующее и снимок), а терминальное (`done`/`error`/`interrupted`) вытесняет самый старый
  элемент и всегда попадает в очередь.
- **мёртвое окно закрывается.** Отправка с таймаутом 5 с: окно, которое не принимает событие,
  отключается и переподключается, получая снимок. Кадры превью — тоже очередь с потерей, а не
  ожидание.
- Отправители — задачи супервизора этапа 6: при закрытии программы они отменяются вместе с остальными
  (`App.stop` зовёт `EventHub.close()` до закрытия сессии).

## 3. Переподключение: сначала состояние

Первое сообщение каждого WebSocket-соединения — `hello`:

```json
{"type": "hello", "engine": true,
 "jobs": [{"prompt_id": "…", "state": "running", "stage": "sample", "step": 3, "max": 8,
           "mode": "video", "prompt": "…", "agent": false, "finalizing": false}],
 "recent": [{"prompt_id": "…", "state": "done", "at": "2026-11-12T10:00:00", "message": ""}],
 "results": [{"id": "…", "prompt_id": "…", "kind": "video", "url": "/api/file/…", …}]}
```

`App.ui_snapshot()` собирает живую очередь, последние исходы (до 100) и результаты этих исходов
(до 60, включая черновики). Окно ([index.html](../../app/ui/index.html), `onSnapshot`) применяет
снимок: добавляет недостающие строки очереди, обновляет состояния, добавляет пропущенные результаты
в Библиотеку, а строки, которые оно считало идущими, закрывает **по фактам снимка** (результат в
`results` или исход в `recent`) — угадывать «наверное, закончилось» оно не пытается.

Это снимок, а не журнал: повторное событие ничего не ломает (обработчики идемпотентны по id), а
пропущенное событие восстанавливается следующим переподключением. Durable outbox не вводился — по
плану он нужен только при доказанной необходимости.

## 4. Агентский API на сервисах и одна таблица ошибок

- Отмена стала операцией сервиса: `App.cancel_job` возвращает данные
  (`finished`/`unknown`/`canceled`/`canceling`/`unconfirmed`/`refused`) и ничего не знает про HTTP.
  Окно показывает уведомление и игнорирует результат; агент переводит его в свои коды. Раньше агент
  вызывал `app.cancel_job` и угадывал состояние по словарю задания.
- Запуск уже шёл через `start_video_job` (этап 4); теперь и ошибки домена проходят через одну таблицу
  ([http_errors.py](../../app/http_errors.py)): `INVALID_PARAM` 400, `JOB_CONFLICT`/код конфликта 409,
  `JOB_NOT_FOUND` 404, `SCHEMA_VERSION` 500. Тот же файл даёт окну `(message, status)`;
  `h_generate_video` пользуется им вместо ручных `except`.
- Единственное оставшееся чтение «чужого» ответа — `web.HTTPException.text` из общего пути (например,
  «нет ноды»): это исключение обработчика, а не разбор HTTP-ответа.
- В отмене появилась честность: если движок не ответил, агент получает `503 COMFY_OFFLINE` (отмена
  записана, но не подтверждена), а если движок отказал — `409 CANCEL_REFUSED`. Документация
  [agent-api.md](../agent-api.md) обновлена.

## 5. Состояния, которые нельзя сломать

| Внутреннее | Публично (`/api/agent/v1`, окно) | Проверка |
| --- | --- | --- |
| `submitting` | `queued` | `test_agent_view`, ответ `POST /jobs` |
| `uncertain` | `queued` + `uncertain: true` в ответе запуска | `test_job_service`, `agent_api_smoke` |
| `finalizing` | `running`, `phase: "finalizing"`, `finalizing: true` | unit + смоук-проба |
| задание прошлого запуска | `queued`, `recovering: true`, `progress.stage: "recovering"` | unit |
| `succeeded`/`failed`/`canceled` | `done`/`failed`/`canceled` (исход в `recent`) | `agent_api_smoke` |

`finalizing` не превращается ни в 404, ни в `done`: окно видит `running` до последнего момента, а
агент — `phase`. `GET /jobs/{id}` для задания из прошлого запуска больше не отвечает 404: оно ждёт
«восстановить» и честно об этом говорит.

## 6. Контракты

Публичные маршруты и события — те же (140 маршрутов, 23 события — [contracts.md](contracts.md);
`hello` — новое сообщение WebSocket, окно его понимает, старые поля сохранены).

| Что | Было | Стало |
| --- | --- | --- |
| доставка событий | `await ws.send_str` на каждое окно | очередь на окно + задача-отправитель, таймаут 5 с |
| `broadcast` | писал `recent` и ждал сокеты | `EventHub.publish`: факт → очередь, без ожидания |
| первое сообщение WS | `{"type": "engine", …}` | `hello` со снимком (включая `engine`) |
| `POST /jobs/{id}/cancel` | 200 или 409 | 200 `canceled`/`canceling`, 503 `COMFY_OFFLINE`, 409 `CANCEL_REFUSED`/`ALREADY_FINISHED` |
| `GET /jobs/{id}` | без `phase` | `phase`, `finalizing`; `recovering` для прошлого запуска |
| таблица ошибок | по местам | [http_errors.py](../../app/http_errors.py) |

Аддитивно: `ui_snapshot` в WebSocket, `phase`/`finalizing`/`recovering` в ответах агента, `503/409`
для отмены. Удаления публичных полей нет.

## 8. Что пока не объединено (честно)

1. **UI-маршруты не разложены по группам.** `build_app` по-прежнему перечисляет 140 маршрутов, а
   обработчики живут методами `App`. Для этого нужен этап 9 («свести server.py к composition root»):
   иначе перенос обработчиков в `http/*.py` потребует передавать весь App, что план как раз запрещает.
   Перенесено то, что даёт измеримый эффект: ошибки, события, состояния, операции агента.
2. **Таблица ошибок используется на путях, которые трогал этап** (агент, `h_generate_video`). Остальные
   UI-обработчики по-прежнему отвечают `web.HTTP*` со своими текстами — это осознанно, чтобы не менять
   публичное поведение массово (§2 плана).
3. **Снимок — не вся Библиотека:** окно получает только результаты последних исходов, остальное оно
   читает при загрузке страницы (`GET /api/library`).
4. **Durable outbox не вводился** (по плану). События могут потеряться при обрыве, состояние — нет:
   снимок при следующем подключении восстанавливает очередь и исходы.
5. **MCP не менялся**: он ходит в тот же агентский API, аддитивные поля ему не мешают.
6. **Запись `recent` живёт в памяти процесса** (200 исходов). После перезапуска исходы видны через
   Библиотеку, как и раньше.
