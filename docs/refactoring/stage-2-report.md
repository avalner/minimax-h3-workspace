# Этап 2. Типы задания и правила переходов

Дата: 12 ноября 2026. План: [architecture-refactoring-plan.md](../architecture-refactoring-plan.md).
Предыдущий этап: [stage-1-report.md](stage-1-report.md).

Задача этапа — описать задание типами, отделить «что просили» от «где оно сейчас» и сделать правила
переходов проверяемыми без aiohttp, без видеокарты и без ComfyUI. Публичные контракты сохранены:
окно и агент видят те же `state`, `prompt_id` и те же ответы.

## 1. Что сделано по пунктам плана

| Пункт | Состояние | Где |
| --- | --- | --- |
| 1. типизированные `JobSpec`, `JobRecord`, `MediaRecord`, ошибки | сделано | [domain/jobs.py](../../app/domain/jobs.py), [domain/media.py](../../app/domain/media.py), [domain/errors.py](../../app/domain/errors.py) |
| 2. раздельное хранение id, backend, schema_version, параметров, результатов | сделано | `JobRecord`, `JobSpec.to_dict()` |
| 3. `prompt_id` остаётся публичным, сопоставление id явное | сделано | `JobRecord.job_id / prompt_id / backend_job_id` |
| 4. переходы created → … → succeeded, отмена как запрос | сделано | `TRANSITIONS`, `JobRecord.apply/request_cancel/cancel_confirmed` |
| 5. failed, canceled, неопределённая отправка; недоступный движок ≠ провал | сделано | `JobState.UNCERTAIN`, тесты |
| 6. модель, ускорение, снимок моделей и LoRA, политика результата в данных | сделано | `JobSpec.model/acceleration/models/loras/result_policy` |
| 7. единый метод перехода с версией записи, прогресс отдельно | сделано | `JobRecord.apply`, `set_progress`, `App.set_job_state` |

## 2. Что теперь где

```text
app/domain/
  errors.py   DomainError, InvalidSpec, InvalidTransition, JobConflict, JobNotFound, SchemaVersionError
  jobs.py     JobState, TRANSITIONS, JobSpec (видео), JobRecord, InputRef, ResultPolicy
  media.py    MediaKind, MediaState, MediaRecord
```

Ни один файл домена не импортирует aiohttp, pywebview, subprocess или `server`. `server.py` и
`agentapi.py` импортируют домен, а не наоборот.

`JobSpec` — это запрос: режим, промпт, seed, длительность, размер кадра, aspect/quality, выбранная
модель и ускорение, снимок имён моделей и LoRA, входные файлы, политика результата, источник.
`JobRecord` — это ход выполнения: внутренний `job_id`, `prompt_id`, `backend`, `backend_id`,
`backend_job_id`, состояние, версия, ошибка, отметки времени, попытки финализации, прогресс и
`MediaRecord`-результаты.

## 3. Правила переходов

```text
created → submitting → queued → running → finalizing → succeeded
                ↘ uncertain ↗        ↘ canceled / failed
```

- `uncertain` — POST мог уйти, а мог и не уйти. Это **не** провал: задание сверяется с движком и
  только потом уходит в `queued`/`failed`. Ветка заведена и проверена, но в сервере пока не
  включается — это durable-отправка этапа 4.
- `finalizing` нельзя отменить: генерация уже состоялась, отмена выбросила бы готовый файл. Поэтому
  из `finalizing` есть только `succeeded`/`failed`.
- Терминальные состояния неизменяемы: позднее событие не переписывает исход. Для цикла WebSocket
  есть `can()` и `try_set_job_state()`, которые не бросают исключение на запоздавшее событие.
- Отмена — просьба: `request_cancel()` ставит отметку, `cancel_confirmed()` меняет состояние. Так
  гонка «отмена против успеха» имеет однозначный исход.
- Версия записи растёт на каждом переходе; прогресс (`stage`, `step`) версию **не** меняет — шаг
  сэмплера не событие для записи.

## 4. Как это подключено к приложению

- `App.queue()` создаёт `JobRecord` вместе с заданием: id, идентичность движка
  (`backend_identity()` — `comfy:<url>` или `cloud:runninghub`), публичный id и спецификация.
  Начальное состояние — `queued`: запись рождается, когда движок уже принял задание (до ответа
  движка отслеживать нечего; настоящее `submitting` — этап 4).
- Все смены состояния идут через `set_job_state()`, который проверяет переход и синхронизирует
  старые поля: `job["state"]` (`queued`/`running`/`error`/`interrupted`) и `job["finalizing"]`.
  Подключены: создание задания (окно и облако), `execution_start`, `execution_error`,
  `execution_interrupted`, финализация, «задание зависло», замена движка, отмена, опрос облака.
- `finalizing` стал настоящим состоянием записи, а окно по-прежнему видит `running`: отображение
  (`public_state`) преобразует внутреннее состояние в прежние слова. `GET /api/job/{pid}` получил
  аддитивное поле `phase` с внутренним состоянием — по нему видно, что происходит на самом деле.
- Политика результата переехала в данные: `JobSpec.result_policy` (`library` или `draft`) решает,
  попадёт ли результат в Библиотеку сразу. Если спецификации нет (остальные режимы пока), остаётся
  прежний флаг `preview` — поведение не меняется.
- Финализация добавляет `MediaRecord` на каждый результат (`library`/`draft`, путь собственной
  копии, файл движка) — это первая реальная запись типа, на котором будет строиться этап 5.

## 5. Выравнивание двух входов (и одно исправление)

Длительность теперь ограничивается в одном месте (`JobSpec.video`), поэтому окно и агент не могут
разойтись в границах. Спецификация видео собирается и в `h_generate_video`, и в `agentapi`, из одних
и тех же полей; тест проверяет, что одинаковый запрос даёт одинаковые `params()` и **одинаковый
граф** `wf.video_graph`.

Найдено и исправлено расхождение: агент собирал LoRA через `custom_loras()` без режима и потому
подмешивал LoRA, которые пользователь выключил именно для видео. Теперь оба входа используют
`custom_loras("video")`. Это изменение поведения агентских заданий (в сторону настроек пользователя),
рецепты и веса не менялись.

## 8. Оставшиеся ограничения (сознательно)

1. **Запись не переживает перезапуск.** Она живёт в памяти рядом с заданием; `queue.json` пока
   хранит прежние поля. Долговечная запись — этап 3 (SQLite).
2. **`submitting`/`uncertain` не включены в сервере.** Правила есть и проверены; сама отправка станет
   транзакционной вместе с ключами идемпотентности в этапе 4.
3. **`job_view` агента читает старые поля** (`job["state"]`), а не запись. Переход на домен в HTTP-
   слое — этап 7; сейчас важно, что отображение состояний уже одно (`public_state`).
4. **Спецификация собирается только для видео.** Остальные режимы создают запись без спецификации и
   сохраняют прежний флаг `preview`; по одному режиму это переносится в этапе 4.
5. **`MediaRecord` — только запись в памяти.** Сервиса (копии, архив, черновики, повторная
   финализация) ещё нет: это этап 5.
6. **`JobRecord.from_dict` пока не используется приложением** — он готов для этапа 3; сейчас его
   проверяет тест сериализации.
7. **Восстановленное задание получает запись без спецификации** (в `queue.json` её нет). Поведение
   прежнее: политика результата берётся из флага `preview`.
