# Этап 3. Долговечное хранилище и миграция

Дата: 12 ноября 2026. План: [architecture-refactoring-plan.md](../architecture-refactoring-plan.md).
Предыдущий этап: [stage-2-report.md](stage-2-report.md), предусловие: [stage-3-precondition.md](stage-3-precondition.md).

Задача этапа — перевести состояние с JSON-файлов на SQLite: библиотека и очередь импортируются один
раз, дальше база — единственный источник истины. Публичные контракты не менялись.

## 2. Схема

```text
schema_migrations  name, version, applied_at, note      — шаги миграции, каждый с маркером
library            id, position, date, fav, kind, mode, prompt_id, payload
jobs               job_id, prompt_id, backend, backend_id, backend_job_id, mode, state, version,
                   created_at, updated_at, record_json
media              media_id, job_id, kind, state, path, library_id, bytes, created_at, error, payload
job_results        job_id, node, subfolder, type, filename, media_id
                   UNIQUE (job_id, node, subfolder, type, filename)
idempotency_keys   key, fingerprint, job_id, created_at
import_problems    name, at, reason, detail — то, что не удалось прочитать при импорте
```

Библиотечная запись хранится целиком в `payload` (вместе с полями, которых эта версия не знает), а
колонки рядом — индексированные копии для сортировки и фильтров. Задание — `record_json` (версия
схемы внутри), результаты — отдельными строками.

`jobs` теперь держит и `graph` (собранный граф) и `legacy` (поля очереди прежней версии: `meta`,
`stages`, `titles`, `preview`). Это временно: этап 4 заберёт их в сервис заданий, зато перезапуск
восстанавливает задание точно, а не догадками.

## 3. Почему одно соединение

Приложение берёт папку данных целиком (этап 0/предусловие), поэтому второй процесс исключён, а все
записи идут с одного потока — потока event loop. Значит, одно соединение, `BEGIN IMMEDIATE` на
короткую транзакцию и никаких `to_thread` с базой: SQLite не ждёт чужой блокировки, а каждая запись
стоит микросекунды. `busy_timeout` всё равно выставлен — чтобы посторонний читатель не подвесил
запись. Длинные операции (скачивание, копирование файлов) в транзакцию не попадают: это правило
записано в docstring модуля, потому что именно оно защищает окно от зависаний.

## 4. Долговечность и копии

WAL + `synchronous=NORMAL`: падение теряет максимум последние коммиты, файл остаётся целым, читатель
не блокирует писателя. У WAL есть спутники `-wal` и `-shm`, поэтому копия базы делается **не**
копированием файла, а `Database.backup_to()` (SQLite backup API) — это работает и на живой базе.

## 5. Миграция

Три названных шага: `0001-schema`, `1000-import-library`, `1001-import-queue`. Каждый выполняется в
одной транзакции вместе со своей записью в `schema_migrations`:

- упавший шаг не оставляет ни половины строк, ни маркера — следующий запуск повторяет его;
- перед первым импортом создаётся `backup/<дата>/`: копии `library.json`, `queue.json`, `config.json`
  и копия базы через backup API;
- **исходные JSON не удаляются** — это последняя линия обороны и то, что читает старая версия;
- битый файл не превращается в пустую библиотеку: шаг не отмечается, проблема пишется в
  `import_problems` и в отчёт, следующий запуск пробует снова;
- записи без `id` (библиотека) и без `graph` (очередь) пропускаются с записью в отчёт, файл остаётся;
- очередь импортируется как `queued` и **ничего не отправляет**: окно спрашивает пользователя, как и
  раньше. Записи старше недели не предлагаются и из таблицы удаляются — прежнее правило очереди.

Отчёт миграции (`applied`, `skipped`, `imported`, `problems`, `backup`) отдаётся в
`GET /api/status` → `storage`.

## 6. Единственный источник истины

- `Library` читает и пишет только в базу; `library.json` больше не обновляется.
- Живая очередь — таблица `jobs`: задание пишется при добавлении и на каждой смене состояния, строка
  удаляется, когда задание уходит из памяти (готово, отменено, снято).
- Восстановление после запуска читает `jobs`, а не `queue.json`; `h_queue_saved`/`resume`/`discard`
  работают с таблицей.
- Двусторонней записи нет: JSON остаются снимком на момент миграции.

Проверено на копии настоящей папки данных (30 записей библиотеки): импорт прошёл, все 30 записей
отдаются из базы, второй запуск ничего не импортировал (`applied` пуст, `skipped` — все три шага), а
переключение «избранного» изменило строку в базе и **не** изменило `library.json` (хеш файла тот же).

## 7. Контракты и формат

| Что | Изменение | Совместимость |
| --- | --- | --- |
| `GET /api/status` | добавлено `storage: {path, schema_version, migration, error, waiting}` | аддитивно |
| `GET /api/queue/saved`, `POST /api/queue/resume`, `/api/queue/discard` | те же ответы, данные из базы | без изменений |
| `GET /api/library`, `PATCH /api/library/{id}`, `/api/preview/keep` | те же ответы | без изменений |
| `queue.json` | больше не пишется | остаётся снимком; старая версия прочитает его как есть |
| `library.json` | больше не пишется | то же |
| `h3studio.db` (+ `-wal`, `-shm`) | новый файл в папке данных | — |

## 8. Восстановление и старая версия

- **Откат к прежним файлам.** Закрыть программу, удалить/переименовать `h3studio.db*`, вернуть старую
  версию. Она прочитает `library.json` и `queue.json` — но только в состоянии на момент миграции:
  всё, что сделано после, в файлах отсутствует.
- **Восстановление из копии.** Взять `backup/<дата>/library.json` (и `queue.json`), положить в папку
  данных при закрытой программе, удалить `h3studio.db*` — следующий запуск импортирует копию заново.
  Копия базы (`backup/<дата>/h3studio.db`) открывается как обычная SQLite, если нужно достать записи
  без импорта.
- **Перемещение папки данных.** Копировать при закрытой программе (WAL схлопывается на закрытии) либо
  через `backup_to()`. Копирование открытой папки файловым менеджером может потерять журнал.
- **База новее программы.** Открытие отказывается с понятной ошибкой (`SchemaVersionError`), файл не
  перезаписывается — это проверено тестом.
- **Битая база.** Приложение стартует, `storage.error` в `/api/status` называет причину; библиотека
  при этом пуста, но файлы и копии на месте.

## 10. Оставшиеся ограничения

1. **`recent` и `history` по-прежнему в памяти** (200 записей): после перезапуска детали давно
   завершённого задания недоступны. База для этого есть — перенос в этапе 7.
2. **Ключи идемпотентности** таблица есть и проверена, но агентский API пока держит ключи в памяти:
   этап 4.
3. **Медиа-строки пишутся при финализации**, но сервиса результатов ещё нет: копия в папку
   результатов остаётся файловой операцией, `.part` и повторное копирование — этап 5.
4. **Ретеншен базы не задан:** `jobs` чистится при уходе задания из очереди, `media` растёт вместе с
   результатами; `VACUUM`/архивации нет — решать в этапе 9.
5. **Старая версия после миграции видит только снимок** на момент импорта: изменения после него для
   неё не существуют. Это цена перехода и она описана в README.
6. **Черновики картинок (`pending`) остаются в памяти** — так и задумано (этап 1, §7 плана).
7. **Одна база на папку данных, одно соединение на процесс.** Второй экземпляр запрещён (предусловие),
   поэтому репликации и «двух читателей из разных процессов» нет.
