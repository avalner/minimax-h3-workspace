## 2. Атомарная запись

`app/storage/atomic.py` — три функции (`atomic_write_bytes`, `atomic_write_text`, `atomic_write_json`)
и ошибка `AtomicWriteError`; зависимостей от aiohttp, окна и приложения нет.

Как пишет: временный файл в **той же папке**, что и цель (значит, `os.replace` — это переименование в
пределах тома, оно атомарно), полная запись, `flush` + `fsync`, `os.replace`, и только потом
`fsync` каталога (на Windows каталоги не открываются — пропускается). Имя временного файла содержит
pid и случайные байты, поэтому две одновременные записи не сталкиваются. При любой ошибке временный
файл удаляется, а цель остаётся прежней. `PermissionError` на `os.replace` повторяется до 5 раз с
нарастающей паузой: на Windows так выглядит краткий захват файла антивирусом или индексатором.

Чего это не обещает (и не должно): не защищает от отказа железа, не спасает копию в другом месте и не
делает транзакцию из файла и SQLite. Гарантия ровно одна: цель — либо старая версия, либо новая.

Куда применено:

| Файл | Было | Стало |
| --- | --- | --- |
| `config.json` (`engine.Config.update`) | прямой `write_text` | атомарно, память меняется только после успешной записи |
| `library.json` (`Library.save/add/remove`) | `tmp` с фиксированным именем, без `fsync` | атомарно; при ошибке `add`/`remove` откатывают и список в памяти |
| `queue.json` (`App.save_queue`) | прямой `write_text`, ошибка молча проглатывалась | атомарно, ошибка запоминается и показывается |
| `long/<run>/project.json` | прямой `write_text` | атомарно |
| `long/<run>/state_<N>.json` | прямой `write_text` | атомарно (сам `.latent` — этап 5) |
| чат `chats/<id>.json` | прямой `write_text` | атомарно |
| workflow `workflows/<id>.json` | прямой `write_text` | атомарно |
| `assets/<id>/<id>.json` (метаданные входа агента) | прямой `write_text` | атомарно |
| `agent.json` (обнаружение агента) | `tmp` с фиксированным именем | атомарно, затем ограничение прав (как раньше) |
| `data_location.txt` и старый `config.json` в `datadir.py` | прямой `write_text` | атомарно |

Не переносилось намеренно: медиафайлы и большие копии (этап 5: потоковая запись через `.part`),
`extra_model_paths.yaml` (это файл ComfyUI, не наше состояние), `last_save_dir.txt` (подсказка окна
«Сохранить как», потеря ничего не стоит), отчёты для разработчика.

## 3. Ошибки сохранения видны

- `Config.update` пишет файл **до** изменения памяти. Не записалось — старые значения остались и в
  памяти, и на диске, а вызывающий код получил исключение (раньше память могла заявлять «сохранено»).
- `Library.add` / `Library.remove` при ошибке откатывают список в памяти и пробрасывают ошибку;
  обработчик отдаёт 500, а не тихое «добавлено».
- `save_queue` вызывается из изменения состояния и потому не бросает исключение в вызывающий код: она
  запоминает `queue_save_error`, пишет `note_error` и отдаёт поле в `/api/status`. Окно получает
  честный признак, что очередь на диске не совпадает с тем, что оно видит.
- `finish_job` при ошибке регистрации не теряет задание: пишет `note_error`, отправляет в окно
  `notice` («Видео готово, но записать его в Библиотеку не удалось…») и оставляет задание в очереди
  для повтора.

Добавленное поле `queue_save_error` — аддитивное: старые клиенты его просто не читают.

Отдельно проверены два места, где ошибка записи **не должна** уносить готовый файл (раньше такая
ошибка там просто не могла возникнуть, потому что `Library.save` не бросала):

- **Сборка FFmpeg**: если запись Библиотеки не удалась, собранный клип не удаляется (старый
  обработчик ошибки удалял `dest`, а вместе с ним и готовое видео). В окно уходит сообщение с путём к
  файлу.
- **Облачный результат (RunningHub)**: то же — файл остаётся на диске, сообщение называет путь.

Порядок «скачали → зарегистрировали → убрали задание из очереди» для облака и FFmpeg пока остался
прежним (это не ComfyUI-путь): он входит в общую финализацию этапа 5.

## 4. `finalizing`: задание не исчезает до результата

`finish_job` больше не делает `self.jobs.pop()` в начале. Порядок теперь:

1. проверка «это уже делается / уже сделано» → повторный вызов (из WebSocket, `reconcile`, гонки
   отмены, сторожа) сразу выходит;
2. `job["finalizing"] = True` и **запись очереди** — рестарт в этот момент узнает, что результат уже
   сгенерирован, и не запустит генерацию заново;
3. поиск выходов в истории движка (`job_outputs`), регистрация записей в Библиотеке (черновики — по
   прежней политике);
4. `finalized = True`, и только теперь `self.jobs.pop(pid)` и `done` в окно.

Согласовано с остальными путями:

- **Отмена** ([cancel_job](../../app/server.py#L3964)) для задания в `finalizing` движок не прерывает:
  генерация уже закончилась, прерывание выбросило бы готовый клип. В окно уходит `notice`.
- **Замена движка** ([drop_engine_jobs](../../app/server.py#L918)) не объявляет потерянным задание,
  чей результат уже пишется.
- **Сторож заданий** пропускает `finalizing`: тишина в это время — не зависшая генерация.
- **`reconcile_jobs`** может звать `finish_job` спокойно: защита от повторной финализации внутри.
- **Рестарт посреди финализации** ([_resume_one](../../app/server.py#L1886)): запись из `queue.json` с
  `finalizing: true` и `pid` сначала сверяется с историей движка; есть выходы — результат забирается
  без повторной генерации.

## 5. Восстановление очереди по одному элементу

`POST /api/queue/resume` ([h_queue_resume](../../app/server.py#L1926)) больше не очищает `saved_queue`
заранее. Каждый элемент восстанавливается сам и покидает сохранённый список **только после успеха**
(и очередь сохраняется после каждого — падение в середине не отправит ничего дважды):

| Что с заданием | Что делает |
| --- | --- |
| движок его ещё держит (running/pending) | берётся под наблюдение (`self.jobs`), повторно не отправляется |
| движок его закончил (есть выходы в истории) | результат регистрируется сразу, генерации нет |
| движок закончил с ошибкой | задание помечается ошибкой (`recent`), повторно не отправляется |
| движок про него не помнит | граф отправляется заново — прежнее поведение |
| движок **не отвечает** | ни один элемент не отправляется и не удаляется; в ответе `unreachable: true` |
| движок отклонил граф (400) | элемент остаётся в `saved_queue` на следующий раз, остальные идут |
| любое другое исключение по элементу | элемент остаётся, остальные восстанавливаются |

Ответ дополнен полями `restored`, `kept`, `unreachable`, `error` (старое `jobs` не изменилось).
Окно при частичном восстановлении показывает предупреждение вместо «Задания вернулись в очередь»
([index.html:2138](../../app/ui/index.html#L2138)).

## 6. «Добавить в библиотеку» идемпотентно

([h_preview_keep](../../app/server.py#L4123)) Черновик уходит из `pending` только после того, как
запись попала в Библиотеку. Если запись не удалась — черновик остаётся черновиком, кнопка работает
снова, ответ 500 с текстом причины. Повторное нажатие (двойной клик, повтор после ошибки) возвращает
тот же элемент и не создаёт второй. Для этого id элемента используется как ключ идемпотентности.

**Отступление от буквы плана:** план называет `finalizing` «временным состоянием». Сделано флагом
`job["finalizing"]` (плюс поле в записи очереди), а публичное `state` осталось `running`/`queued`.
Причина: `state` читают окно, `/api/job` и `job_view` агента; новое значение в публичном поле сломало
бы контракт до этапа 7, где появятся совместимые адаптеры. Явная машина состояний — этап 2; там
`finalizing` станет состоянием, а `job_view` и окно получат отображение.

## 7. Изменения формата данных

| Данные | Изменение | Совместимость |
| --- | --- | --- |
| `queue.json` | у записи появилось поле `finalizing` | старый файл без поля читается как `False`; миграция не нужна |
| `library.json`, `config.json`, проекты, чаты, workflow | формат тот же, запись атомарная | прежние файлы читаются; неизвестные поля сохраняются (проверено тестом на фикстурах) |
| `job` в памяти | добавлены `finalizing`, `finalize_tries`, `finalized` | наружу отдаётся только `finalizing` в `/api/job` |

Порядок восстановления после сбоя: обычный запуск → `load_queue` → вопрос пользователю → `resume`.
Специальной миграции нет, откат не нужен: старый файл очереди просто не имеет нового поля.

## 9. Оставшиеся ограничения (сознательно, до следующих этапов)

1. **Нет машины состояний и сервиса заданий.** `finalizing` — флаг, а не состояние; правила переходов
   живут в `App`. Это этапы 2 и 4.
2. **Регистрация результатов не транзакционна с файлами.** Копия результата (`archive_item`) всё ещё
   пишется прямо в целевой файл, без `.part`, без проверки размера, и потоково не скачивается для
   больших видео. Это этап 5 (плюс там же повторное копирование при ошибке архива). Там же —
   уникальность результата по «задание + выход движка»: сейчас повторная финализация задания с
   несколькими картинками могла бы добавить уже добавленные (для одного видео это невозможно:
   выход один, а неудачная запись списка ничего не добавляет).
3. **Черновики по-прежнему только в памяти** (`PREVIEW_LIMIT = 40`). Долговечное восстановление
   заданий их не касается — так и задумано.
4. **`queue.json` пишется целиком на каждое изменение очереди.** Для десятков заданий это нормально;
   с SQLite (этап 3) уйдёт.
5. **Идемпотентность агента** всё ещё в памяти (этап 4).
6. **Второй экземпляр приложения** на одном `H3STUDIO_DATA` не запрещён: это предусловие этапа 3,
   вместе с предупреждением о `DATA_DIR` на сетевой папке (WAL поверх SMB опасен).
7. **`fsync` на каждую запись очереди** добавляет единицы миллисекунд; при пакетной работе (много
   картинок подряд) это заметно только по логу, не по интерфейсу. Если станет мешать — уменьшать
   частоту записи, а не отключать `fsync`.
8. **Зависшая финализация не снимается сторожем.** Сторож заданий теперь пропускает `finalizing`, а
   отдельного таймаута финализации нет: если запись результата встала навсегда, задание останется в
   очереди видимым и будет повторено при следующем запуске (или на следующем `reconcile`). Снимать
   такие задания по таймауту — этап 5, вместе с повторяемой финализацией.
9. **Окно, exe и MCP** не проверялись в этой сессии (нет pywebview и PyInstaller; MCP требует
   запущенного экземпляра). Это записано в §8 этапа 0.
