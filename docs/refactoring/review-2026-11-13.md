## 1. [P1] save_queue удаляет отправляемые и неопределённые задания

Место: `app/routes/jobs.py`, `JobRoutes.save_queue`, строки 92–97. Связанный путь: `app/services/jobs.py`, `submit`/`submit_idempotent`; `app/application.py`, `start_video_job`.

`JobService` сначала записывает submitting в БД, затем ожидает ответ backend. В `self.jobs` запись появляется только после успешной отправки через attach_job. При потере ответа uncertain тоже остаётся только в БД. Но save_queue считает все нетерминальные строки, отсутствующие в self.jobs/pending_resume/resume_cloud, удалёнными заданиями и стирает их.

Поэтому завершение/добавление другого задания во время отправки или обычный shutdown удаляют именно ту запись, которая нужна для восстановления неопределённой отправки. Ключ idempotency остаётся со ссылкой на удалённую запись; повтор получает IDEMPOTENCY_LOST.

Воспроизведено на настоящем App и SQLite с backend, остановленным asyncio.Event:

```text
SUBMIT before save_queue= submitting
SUBMIT after save_queue= None
UNCERTAIN before save_queue= uncertain
UNCERTAIN after save_queue= None
idempotency_keys: ключ и job_id остаются
```

Исправление: убрать удаление записей БД по разнице с UI-кэшем. Удаление/отказ/завершение должны быть явными операциями репозитория и сервиса. БД остаётся источником истины, включая задания без backend_job_id. Не ограничиваться добавлением одного статуса в исключения: нужно сохранить все стадии между durable create и attach.

Регрессия: параллельно отправлять одно задание, завершать другое, вызывать shutdown и затем открывать приложение повторно. Проверить submitting/uncertain и повтор ключа после рестарта.

## 2. [P1] Облачная финализация удаляет задание до сохранения результата

Место: `app/routes/jobs.py`, `poll_cloud`, строки 342–374, особенно `self.jobs.pop(pid, None)` на строке 352.

После скачивания файла задание ещё finalizing, но уже удаляется из self.jobs. JobStore вызывает save_queue, который удаляет нетерминальную строку из БД. Только затем создаётся library item и записывается succeeded. Сбой процесса в этом промежутке лишает приложение возможности восстановить результат. При отказе library.add метод сообщает ошибку и возвращается, оставляя и очередь, и БД без задания.

Воспроизведение: fake RunningHub возвращает SUCCESS и mp4; fake session отдаёт один байт; library.add выбрасывает OSError.

```text
CLOUD after Library failure: live=[] durable=None library=0
```

Исправление: провести облачные результаты через долговечный идемпотентный финализатор с постоянным media ID, зафиксировать результат и succeeded до удаления из активной очереди. При сбое оставить finalizing/retry, не перезапускать платную генерацию. Скачать файл повторно при необходимости допустимо; повторно генерировать — нет.

Регрессия: ошибка записи библиотеки и аварийное завершение после скачивания, до/после commit; после старта тот же task ID завершается одним результатом без нового create.

## 3. [P1] Независимая копия черновика недоступна после рестарта

Место: `app/services/media.py`, `MediaService.keep`, строки 527–529; чтение — `App.file_path`.

keep сначала пишет library item, затем archive добавляет item.local только в память. _save_media сохраняет путь в таблицу media, но library payload больше не обновляется. При запуске Library читает payload, а file_path ищет local внутри него, не используя media.path.

После очистки ComfyUI output приложение считает файл потерянным, хотя независимая копия действительно существует.

Воспроизведено с настоящим копированием небольшого тестового файла:

```text
ARCHIVE memory local= ...\copies-0\20261113_draft123_clip.mp4
ARCHIVE reloaded local= None
media.path= ...\copies-0\20261113_draft123_clip.mp4
после удаления только тестового исходника: public.missing=True
копия в results при этом существует
```

Исправление: после архивирования долговечно сохранить ссылку и статус; обеспечить согласованное чтение из выбранного источника истины. Учесть сбой между rename и сохранением пути и повтор keep уже существующего item.

Регрессия: добавить черновик в библиотеку → закрыть БД → открыть заново → очистить тестовый output → запросить файл через API; он должен отдаваться из независимой копии.

## 4. [P1] Запрет записи в более новую схему БД фактически не действует

Место: `app/application.py`, конструктор App, строки 81–91.

migrate корректно выбрасывает SchemaVersionError, но App перехватывает его общим except, записывает строку migration_error и продолжает создавать все пишущие репозитории. Приложение затем работает с несовместимой схемой. Это нарушает явно заявленное ограничение и создаёт риск повреждения данных при запуске старой версии.

Воспроизведение: в новой тестовой БД добавить schema_migrations с version=SCHEMA_VERSION+1, закрыть и снова создать App; затем вызвать library.add.

```text
FUTURE schema error= SchemaVersionError: ... писать в такую базу нельзя.
FUTURE schema writable=1
```

Исправление: для неизвестной версии схемы остановить создание пишущего приложения и закрыть соединение; сообщить ошибку через существующий startup error path. Если нужен диагностический режим, он должен быть действительно read-only и исключать миграции/submit/изменения библиотеки.

Регрессия: открыть future-schema БД через build_app/ServerThread; проверить отказ старта или запрет всех записей, а не только прямой вызов migrate.

## 5. [P2] Черновики после перезапуска самовольно попадают в библиотеку

Место: `app/services/media.py`, `MediaService.finalize`, строка 399.

Внутри транзакции library.repo.add(item) выполняется и для draft, и для library policy. В текущем запуске draft не добавляется в library.items, поэтому тесты и экран его не показывают. Но строка уже существует в таблице library без признака preview: hold_draft добавляет этот признак после записи. На следующем запуске Library.load показывает черновик как обычный библиотечный результат.

Воспроизведение: App.finish_job для задания preview=True, затем создать новый Library на той же БД.

```text
DRAFT current_library=0 pending=1 reloaded_library=1
```

Уточнение требования пользователя от 13 ноября 2026: черновик должен сохраняться после перезапуска и оставаться черновиком до явного добавления в библиотеку или удаления. Исчезновение pending после рестарта не является допустимым исправлением. Ранее план ошибочно трактовал хранение в памяти как поведение, которое следует сохранить; это ограничение плана исправлено.

Исправление: долговечно сохранять запись, статус, параметры и доступный файл черновика отдельно от library; восстанавливать черновики в соответствующих разделах при запуске; добавлять строку library только при library policy или явном keep. Не исправлять одним фильтром UI или исключением записи в library без восстановления черновика: нельзя ни превращать черновик в библиотечный результат, ни терять его. PREVIEW_LIMIT может ограничивать кэш/отображение, но не срок хранения черновиков.

Регрессия: финализировать черновик → реально переоткрыть БД/приложение → черновик остаётся доступен в своём разделе с тем же ID и рабочим файлом, библиотека остаётся без него; повторить перезапуск; после keep item появляется в библиотеке ровно один раз, перестаёт быть черновиком и сохраняется после следующего запуска. Дополнительно проверить количество черновиков выше прежнего PREVIEW_LIMIT и очистку временных файлов: сохранённые черновики не теряются.

## 6. [P2] Повтор одинакового API-запроса без seed получает конфликт

Место: `app/agentapi.py`, _submit, строки 499–501; `app/services/jobs.py`, spec_fingerprint.

Для каждого запроса без seed выбирается новое случайное значение до поиска idempotency key. Fingerprint включает seed, поэтому тот же самый входной JSON с тем же ключом превращается в «другой запрос». С загрузками изображений есть аналогичный риск: повторно создаваемое случайное имя ComfyUI входит в InputRef и fingerprint.

Воспроизведено через настоящий AgentAPI._submit и JobService с fake backend:

```text
первый {mode:video,prompt:test,idempotency_key:same-request}: 202, job=p1
повтор того же JSON: 409 IDEMPOTENCY_CONFLICT
backend submits=1
```

Исправление: идентичность исходного запроса вычислять по стабильным клиентским данным до генерации случайных defaults и загрузки файлов. Для повтора возвращать уже сохранённые seed/spec/refs. Изменение явного seed или содержимого запроса должно по-прежнему давать конфликт. Сначала определить ключ, затем выполнять дорогие/изменяющие операции.

Регрессия: два одинаковых text-to-video запроса без seed, image-to-video с фиксированным seed, параллельные запросы и повтор после рестарта. Все возвращают исходное задание с исходными параметрами.

## 7. [P2] Обработчик ошибки сохранения сам падает с NameError

Место: `app/application.py`, `set_job_state`, строка 795 и список импортов из webcommon в начале файла.

После разделения server.py имя STORE_ERRORS в application.py не импортировано. При отказе jobs_repo.save Python не может вычислить тип except, и вместо записи ошибки/сохранения состояния выдаёт NameError.

Воспроизведение: для record вне self.jobs подменить jobs_repo.save на OSError и вызвать set_job_state(..., FAILED).

```text
NameError: name 'STORE_ERRORS' is not defined
```

Исправление: добавить корректный импорт и интеграционный тест этого пути на уровне App. Дополнительно проверить неопределённые имена статическим анализом после переноса методов между модулями.

## Незакрытые требования плана

Это отдельный вывод по охвату работы, а не требование механически соблюдать исходные имена файлов.

1. **Долговечная отправка реализована только для video.** App.queue (`application.py:1127–1146`) по-прежнему отправляет POST /prompt до создания JobRecord для остальных режимов. queue_cloud также вызывает create до записи задания. Тот же сбой между принятым запросом и локальной регистрацией продолжает терять задания. FFmpeg вообще живёт в отдельном ffmpeg_jobs, без долговечного JobRecord. План требовал подключить остальные режимы и все пути финализации.
2. **HTTP пока не стал тонким слоем.** App наследует восемь route mixins, которым доступен весь App. routes/jobs.py управляет хранилищем, восстановлением, watchdog и облачной финализацией; AgentAPI продолжает читать внутренние коллекции App. Перенос методов сократил server.py, но не завершил разделение ответственностей. Исправление save_queue через UI-кэш особенно важно сделать в сервисе/репозитории, иначе связанность останется источником потерь.
3. **Собранное приложение не проверено.** Включение всей папки ui в spec — полезное изменение, но не доказательство работоспособности exe, динамических импортов и WebView2. До полной приёмки нужны build и запуск новой/обновлённой установки на тестовых данных.
4. **Существующие тесты не проверяют важные границы.** Проверки черновиков смотрят на список в памяти, а не на переоткрытую БД; idempotency проверяется со стабильным явным seed; отдельные unit JobService не вызывают App.save_queue во время отправки. Добавить сквозные проверки выше, не ограничиваться новыми unit-тестами отдельных слоёв.

## Рекомендуемый порядок исправлений

1. Устранить удаление долговечных записей по состоянию UI-кэша и исправить облачный commit-before-remove.
2. Исправить сохранение archive path и запрет работы с future-schema БД.
3. Разделить draft/library на уровне хранения, исправить нормализацию idempotency и импорт STORE_ERRORS.
4. Добавить сквозные проверки найденных сценариев; заново выполнить основной набор.
5. Завершить общий lifecycle для остальных режимов/FFmpeg, затем сокращать ответственность route mixins и провести проверку сборки.

После этих исправлений можно повторно оценить приёмку. Текущие 33 зелёные проверки подтверждают значительную часть обычных сценариев, но не заявленную надёжность восстановления после сбоя.
