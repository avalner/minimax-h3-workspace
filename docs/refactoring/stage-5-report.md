# Этап 5. Медиасервис и одна финализация

Дата: 12 ноября 2026. План: [architecture-refactoring-plan.md](../architecture-refactoring-plan.md).
Предыдущий этап: [stage-4-report.md](stage-4-report.md).

Задача этапа — собрать результат задания в одном месте: найти выходы движка, проверить их, аккуратно
скопировать файл (`.part` → размер → переименование), записать записи о файле, библиотеку и
`succeeded` одной транзакцией и уведомить окно. Генерация, копия, черновик, запись Библиотеки и
архивная копия — разные сущности с разными исходами; сбой копии больше не выглядит как сбой
генерации, а повтор финализации не создаёт второй ролик.

## 1. Что сделано по пунктам плана

| Пункт | Состояние | Где |
| --- | --- | --- |
| 1. `MediaService`/репозиторий, пять разных сущностей | сделано: `MediaRecord` + состояния `archive_failed`, `media_id_for` | [domain/media.py](../../app/domain/media.py), [services/media.py](../../app/services/media.py) |
| 2. общая финализация: finalizing → outputs → файлы → транзакция → уведомление | сделано; тело `App._finish_job` — один вызов сервиса | §2 |
| 3. потоковая запись в `.part`, статус, размер, атомарное переименование | сделано для скачивания и для локальной копии | §3 |
| 4. большие файлы вне event loop, кооперативный токен и ожидание writer | сделано в `MediaFiles.copy_file` | §3 |
| 5. правила восстановления до/после rename и до/после commit | описаны в докстроке сервиса и здесь | §4 |
| 6. архивирование отдельным статусом, повтор копии без новой генерации | сделано: `archive_failed`, `archive_item()` | §5 |
| 7. идемпотентное «Добавить в библиотеку», id записи, недописанное не публикуется | сделано: id выводится из выхода движка, строка пишется после renaming | §6 |
| 8. очистка только известных временных файлов | сделано: только `.<имя>.<pid>.<random>.part` в своих папках, без активных writers и ссылок | §7 |

## 2. Финализация — один путь

```text
finished-событие / сторож / сверка / возобновление
  → App.finish_job(job)                     finalizing в память и в базу, защита от повтора
  → MediaService.finalize(job, notify)      находит выходы, выбирает результат по политике
      → outputs_of(pid)                     App.job_outputs (повторные вопросы к /history)
      → on_outputs(job, refs)               состояние сцены длинного видео, тоже через .part
      → archive(item)                       копия: .part → размер → os.replace
      → library.repo.add + media.save + results.register + record.succeed + jobs.save
        (одна транзакция SQLite)
  → Library.note_committed(item)            только после COMMIT — окно видит готовое
  → notify({"type": "done", ...})           то же событие, что было раньше
```

Порядок фиксирован и является правилом восстановления: файл появляется под настоящим именем
**до** транзакции, записи — только после того, как файл целый. Обратный порядок дал бы строку
Библиотеки, за которой нет файла.

## 3. Файлы: `.part`, размер, переименование, отмена

- `MediaFiles.save_stream(dest, chunks, expected_bytes=...)` — скачивание: уникальный
  `.<имя>.<pid>.<random>.part` рядом с целевым файлом, запись чанками (1 МиБ), `fsync`, проверка
  размера, `os.replace`. Целиком в память не читается ни видео, ни `.latent`.
- `MediaFiles.copy_file(src, dest)` — локальная копия в рабочем потоке через `asyncio.to_thread`,
  тоже через `.part`. Поток проверяет `CancelToken` между чанками: отмена `to_thread` поток не
  останавливает, поэтому вызывающий ставит токен, **ждёт** возврата потока (поток сам убирает свой
  `.part`) и только затем сообщает отмену. Это проверено тестом с заблокированным writer.
- HTTP-статус проверяет backend (`ComfyBackend.open_output`), размер — сервис; завершённость
  передачи видна как несовпадение с `Content-Length` или как исключение чтения.
- Ожидаемый размер, если движок его не назвал, для локальной копии берётся из файла-источника.
- Известное ограничение: отмена во время `fsync` скачивания может оставить `.part` (не готовый
  файл) — его уберёт очистка следующего запуска; на Windows удаление открытого файла невозможно.

## 4. Файловая система и SQLite — не одна транзакция

Правила восстановления, реализованные порядком операций и стабильными именами:

| Сбой | Что осталось на диске | Что видит пользователь | Что делает повтор |
| --- | --- | --- | --- |
| до rename | только `.part` | ничего | скачивает заново, старый `.part` убирает очистка |
| после rename, до commit | полная копия, нет строк | ничего (окно не видело) | находит копию по имени `*_<id>_<файл>` и не качает второй раз |
| после commit | копия + запись + `succeeded` | готовый ролик | не повторяется: задание уже `succeeded` |

Имя копии стабильно: `{дата}_{media_id}_{файл}`, а `media_id` выводится из «задание + узел +
subfolder + type + filename» (`media_id_for`). Поэтому второй попытке не нужно помнить первый
запуск, чтобы не сделать вторую копию и второй item.

## 5. Архивная копия — отдельный статус

`MediaState.ARCHIVE_FAILED` (схема `MediaRecord` 2) означает: запись в Библиотеке есть, независимой
копии нет; `error` хранит причину. Копия не удалась — задание всё равно `succeeded`, окно получает
готовый результат, а `h_results_get` по-прежнему показывает `nocopy`. `MediaService.archive_item()`
повторяет копию без новой генерации (кнопка «Результаты», повторное добавление в библиотеку).

## 6. Библиотека и черновики

- Id элемента Библиотеки = `media_id`, выведенный из выхода движка: повторная финализация — это
  обновление той же строки (`INSERT ... ON CONFLICT` в `library`, id в памяти проверяется).
- Строка Библиотеки и медиазапись пишутся в одной транзакции с `job_results` и `succeeded`;
  в память окна элемент попадает только после `COMMIT` (`Library.note_committed`).
- Черновик (`ResultPolicy.DRAFT`) по-прежнему живёт в `pending` (память) и не попадает в Библиотеку
  сам; `media` хранит его состояние `draft`. Политика после рестарта не изменилась: черновики
  забываются, как и раньше, — это осознанное решение этапа.
- «Добавить в библиотеку» идемпотентно: `library.get(id)` возвращает уже сохранённый элемент,
  `MediaService.keep` пишет строку (может бросить — черновик остаётся) и затем делает копию.

## 7. Очистка временных файлов

`MediaService.cleanup()` вызывается при старте приложения и удаляет **только** файлы своего шаблона
`.<имя>.<pid>.<random>.part` в папке результатов и в `cloud`/`cache`. Он пропускает `.part`, которым
владеет живой writer (`MediaFiles.active_parts`), и те, на которые ссылаются записи `media` или
элементы Библиотеки. Чужие `*.part` (например, `имя.part` загрузчика LoRA) не трогает.
`App.stop` вызывает `MediaService.shutdown()`: токены отменяются, сервис ждёт writers до 10 с и
ничего не удаляет сам.

## 8. Контракты

Публичные HTTP/WebSocket-контракты не менялись: `/api/job`, `/api/library`, `/api/results`,
`/api/preview/keep`, события `done`/`error` — те же поля. `docs/agent-api.md` не менялся, контракты
агента не затронуты.

Внутренние изменения:

| Что | Было | Стало |
| --- | --- | --- |
| `MediaRecord` | схема 1, состояния `backend/local/draft/library/archived/missing` | схема 2, плюс `archive_failed`; старые файлы читаются |
| `Backend` | `download(record, ref, destination)` | `open_output(ref) -> OutputStream(chunks, expected_bytes)` |
| элемент Библиотеки | случайный `uuid4` id, `local` ставился копией | id из выхода движка; `local` ставится после `.part` → rename |
| `media` таблица | строка на результат | та же схема, добавлены значения состояний |

Миграции схемы нет (таблицы не менялись); новый код читает старые записи `media` (схема 1) и пишет
новые (схема 2). Откат на предыдущую версию после записи `archive_failed` прочитает такую запись с
ошибкой версии — это ожидаемое поведение более старой сборки.

## 10. Что пока не объединено (честно)

1. **Облако и FFmpeg не адаптеры.** У них остались свои пути отправки, отмены и регистрации; общими
   с этапом 5 стали потоковая запись (`MediaFiles.save_stream`) и копия (`MediaService.archive`).
   `MediaService.finalize` — это финализация пути ComfyUI; после превращения облака в backend он
   будет звать тот же метод.
2. **`job_results` живёт, пока живёт строка задания.** Успешное задание уходит из `jobs` (историческое
   поведение), и строки `job_results` удаляются каскадом; `media` остаётся (job_id → NULL).
   Защита от второго item после этого — стабильный `media_id` и запись Библиотеки, а не уникальный
   индекс `job_results`.
3. **Черновики по-прежнему только в памяти**, медиастрока о них остаётся.
4. **`job_view` агента и HTTP-слой читают старые поля** (`job["state"]`) — этап 7.
5. **`h_upscale`, монтаж, копии для деталей** читают файлы целиком: это не путь результата задания,
   их перенос — отдельно (монтаж станет FFmpeg-адаптером на этапе 6/9).
6. **Скачивание при отмене** может оставить `.part` до следующей очистки (см. §3).
