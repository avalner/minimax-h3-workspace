Задача этапа — вынести отправку и жизнь задания из обработчиков в сервис, описать движок небольшим
протоколом и сделать отправку долговечной: с состоянием «отправляю», честной неизвестностью и
ключом повторного запроса в базе. Публичные контракты сохранены.

## 2. Поток видео-задания

```text
окно / агент
  → JobSpec.video(...)                 одна и та же проверка и одинаковые параметры
  → App.start_video_job(spec, meta)    подготовка движка (VRAM, /free), затем сервис
  → JobService.submit_idempotent       ключ, запись состояния, вызов backend
  → ComfyBackend.submit(spec)          граф из workflows.py по снимку моделей + POST /prompt
  → JobRepository.save(record)         submitting → queued, id движка, граф
  → App.attach_job(record, meta)       очередь окна и таблица `jobs`
```

Сервис не знает aiohttp и окна: он возвращает `JobRecord` и бросает ошибки домена. Backend не получает
`App` целиком — только клиент HTTP, снимок моделей и LoRA. Обработчики остаются тонкими: разбор формы
и статусы HTTP.

## 3. Долговечная отправка

1. Запись создаётся в `created`, переходит в `submitting` и **сохраняется до POST**.
2. Ответ движка записывает `backend_job_id` (и `prompt_id` — публичный id остаётся прежним), затем
   `queued`.
3. Если движок отказал (`SubmitRejected`) — `failed` с его причиной, HTTP 400; ничего не создано.
4. Если движок не ответил — `uncertain`. Это **не** провал и **не** повод отправить снова: POST мог
   уйти. Автоматического повтора нет; `submit` для такого задания запрещён (`JobConflict`), а новый
   заход — это явный `retry()` (новое задание) или сверка.
5. В записи хранится `backend_id` (`comfy:<url>` или `cloud:runninghub`). Возобновление задания
   сверяется с ним: если пользователь сменил движок, задание ждёт свой прежний и не уходит на другой —
   иначе получился бы другой клип за его спиной.

## 4. Идемпотентность

- Ключ резервируется в таблице `idempotency_keys` **до** первого внешнего вызова; в записи остаются
  отпечаток нормализованного запроса (`JobSpec.params()`) и `job_id`.
- Тот же ключ и тот же отпечаток → возвращается то же задание, `deduplicated: true`, ответ `200`
  (как и раньше). Другой отпечаток → `409 IDEMPOTENCY_CONFLICT`.
- Два одновременных запроса: второй ждёт завершения первого (событие в памяти процесса) и получает его
  задание — одного POST достаточно.
- Повтор после перезапуска: ключ и запись в базе, задание возвращается без нового рендера.
- `client` остаётся текстом в `origin`, а не доверенной личностью.

`deduplicated` больше не живёт в памяти `AgentAPI`: старый словарь на 200 ключей удалён.

## 5. Отмена и «остановить текущее»

- Отмена — просьба: `record.request_cancel()` ставит отметку; для ждущего задания движок подтверждает
  сразу (удаление из очереди), для идущего — только после его события или сторожа.
- Отменить `finalizing` нельзя: генерация уже состоялась, отмена выбросила бы готовый клип.
- **Неизвестный id больше не прерывает то, что сейчас идёт.** Раньше `POST /api/interrupt` без
  известного задания отправлял `/interrupt` со всем, что на движке; теперь это отдельная операция
  `stop_current()` и отдельный путь запроса без `prompt_id` (совместимый адаптер для кнопок окна:
  они всегда присылают id).
- Облако и FFmpeg сохранили свои особые пути; задания без записи (старый каталог до миграции)
  обслуживаются прежним кодом.

## 7. Что пока не объединено (честно)

1. **Тело финализации остаётся в `App`.** WebSocket, сторож, `reconcile` и возобновление по-прежнему
   зовут `finish_job`; все они проходят один и тот же путь переходов (`set_job_state` → правила домена)
   и одну защиту от повторной финализации, но поиск файлов, Библиотека и копия живут в `App` до этапа 5,
   где появится `MediaService`.
2. **Остальные режимы (картинки, lipsync, refs, long, montage) собирают граф в обработчике** и идут
   прежним `queue()`; `JobSpec` пока описан для видео. Режимы переносятся по одному — это следующий шаг
   этого же этапа по плану.
3. **Облако и FFmpeg не адаптеры**: у них свои пути отправки/отмены, как и было.
4. **`retry()` есть в сервисе, но HTTP-эндпоинта для него нет**: повтор из окна по-прежнему отправляет
   новое задание обычным путём.
5. **`job_view` агента читает старые поля** (`job["state"]`), а не запись; переход на домен в HTTP-слое —
   этап 7.
6. **Скачивание файлов** в адаптере объявлено, но использует внедряемый поток; потоковая запись с
   `.part` — этап 5.
