## Особенности этой машины (не переоткрывать)

- Системного `python`/`py` в PATH нет (алиас Microsoft Store выключен). Рабочий интерпретатор —
  `_test\venv\Scripts\python.exe` (3.13.14).
- В `_test\venv` нет `pip`, и поставить его не удаётся: `ensurepip` падает на временных папках под
  ограниченным токеном. Пакеты **не устанавливаются**: `aiohttp` и `certifi` берутся на чтение из
  `site-packages` переносимого ComfyUI через `PYTHONPATH`. В ComfyUI пользователя ничего не пишется.
- `python_embeded` изолирован (`._pth`): запускать через него `tests/run.py` нельзя, только через venv.
- `tempfile.mkdtemp` создаёт папку с правами, которые не наследуются, и под ограниченным токеном в
  неё нельзя писать. Поэтому в тестах — `tests/tempdir.py` (`mkdir`, база `_test/tmp`).
- Папка `.git` однажды оказалась без прав пользователя: git не мог писать индекс. Починено скриптом
  из скилла `diagnose-windows-sandbox-acl`; резервная копия и команда отмены —
  `_test/acl-reports/acl-backup-*.json` и `.ps1`. Если git снова не может писать — это тот же случай.
- `_test/` в `.gitignore`; там же временные папки прогонов, копии реальных данных не остаются.

## Договорённости по работе

- Один этап — один коммит (крупный можно двумя: «слой» и «переключение»), сообщения по-английски в
  стиле `<область>: что сделано`, тело — по-русски с деталями.
- Перед коммитом: `tests/run.py` зелёный, `git diff --check` чистый, `git status` без лишнего.
- После этапа — отчёт `docs/refactoring/stage-N-report.md` по формату плана §7: что сделано по
  пунктам, контракты, команды и результаты, миграция/восстановление, ограничения, следующий этап.
- Отвечать и писать документацию по-русски; код и комментарии — по-английски, как в проекте.
- **Не менять рецепты `app/workflows.py`** (шаги, вес LoRA, размеры, seed) во время структурных
  переносов. `video_fused_graph_test.py` это сторожит.
- Публичные контракты (`/api/*`, `/api/agent/v1/*`, `agent.json`, MCP) — только аддитивно, если этап
  не говорит обратного.
- План — не разрешение переписать всё: каждый этап оставляет рабочее приложение и коммит.

## Состояние дел на конец этапа 6 (что уже решено и не пересматривается)

- Домен: `JobState` с переходами, `JobRecord` с `graph`/`legacy`, `JobSpec` (пока видео),
  `MediaRecord` (схема 2, состояние `archive_failed`). `finalizing` — настоящее состояние записи,
  публично показывается как `running`; `/api/job` отдаёт аддитивное `phase`.
- Хранилище: SQLite `h3studio.db`, таблицы `schema_migrations`, `library`, `jobs`, `media`,
  `job_results`, `idempotency_keys`, `import_problems`. JSON-файлы импортируются один раз и больше не
  пишутся (остаются снимком и путём отката). Копия перед импортом — `backup/<дата>/`.
- Очередь: живая очередь = таблица `jobs`; `save_queue()` пишет записи, удаляет ушедшие из памяти;
  возобновление после старта читает `jobs`, не `queue.json`.
- Отправка: одна на оба входа — `App.start_video_job` → `JobService.submit_idempotent` →
  `ComfyBackend.submit`. `submitting` до POST, `uncertain` при молчании, `backend_id` защищает от
  отправки на другой движок.
- Ключи повторных запросов — в базе, с отпечатком; конфликт — `409 IDEMPOTENCY_CONFLICT`; повтор после
  рестарта отдаёт то же задание; два одновременных — один POST.
- Отмена: запрос до подтверждения движком; `finalizing` не отменяется; неизвестный id больше не
  прерывает текущее — для этого есть `stop_current()`.
- Финализация: `App.finish_job` (защита от повтора, `finalizing` в базе) зовёт
  `MediaService.finalize`; результат, копия, черновик, запись Библиотеки и архивная копия — разные
  сущности. Файл публикуется через уникальный `.part` → размер → `os.replace`; строки `media`,
  `job_results` и `succeeded` пишутся одной транзакцией **после** появления файла.
- Id элемента Библиотеки = `media_id` из «задание + узел/subfolder/type/filename»: повтор
  финализации обновляет ту же строку. Ошибка архивной копии — состояние `archive_failed` и повтор
  копии без новой генерации.
- Очистка при старте удаляет только свои `.<имя>.<pid>.<random>.part`, без активных writers и ссылок
  из записей; `App.stop` зовёт `MediaService.shutdown()` и ждёт writers.
- Фоновые задачи: всё, что живёт дольше запроса, идёт через `App.tasks` (`TaskSupervisor`): имя,
  ссылка, ошибка в `recent_errors`/отчёт, отмена и `close()` при остановке. `create_task` в
  обработчике — больше не способ запускать фоновую работу; имя и владелец ресурса обязательны
  (таблица — в `stage-6-report.md` §2).
- Движок: `App.engines` (`EngineManager`) — единственный владелец процесса ComfyUI, один перезапуск
  за раз (остальные ждут и получают тот же ответ), VRAM-рукопожатие с ассистентом (`prepare`), при
  выходе останавливается только наш процесс, пользовательский — нет.
- Закрытие: `App.stop` = запрет новых задач → флаги установок → отмена циклов → ожидание writers →
  `save_queue()` → закрытие сессии → закрытие базы → остановка нашего движка. Бюджет: 15 (дренаж
  обработчиков) + 8 (состояние) + 20 (движок) < 45 с в `main.py`. Незавершённое попадает в
  `App.last_shutdown`, `/api/status.shutdown` и отчёт.
- Облачное задание переживает закрытие окна: запись не попадает в «восстановить?», при старте
  `watch_cloud_jobs()` снова следит за той же удалённой задачей; выключенное облако сохраняет запись.
- `main.py`: ошибка старта сервера показывается в окне, URL для несуществующего сервера не
  открывается; цикл закрывается, поток дожидается.
- Остальные режимы (картинки, lipsync, refs, long, montage) всё ещё собирают граф в обработчике и идут
  прежним `App.queue()`; облако и FFmpeg — своими путями (но уже с потоковой записью результата и
  общим владением задачами). Это осознанно, перенос по одному.

## Следующий шаг — этап 7 плана

Задача: отделить HTTP и доставку событий. Пункты — в плане §4 «Этап 7», кратко:

1. `AgentAPI` на `JobService`/`MediaService`; убрать разбор `response.text` и прямое изменение
   `App`-словарей; затем группы UI-маршрутов.
2. Одно отображение прикладных ошибок в существующие HTTP-форматы, различие статусов UI/API — тестами
   контракта, без массового «выравнивания» поведения.
3. `submitting`/`finalizing`/`recovering` — в совместимые состояния `/api/agent/v1` и WebSocket.
4. Сохранение исхода отвязать от `broadcast`/`remember`; события — после commit.
5. Медленный WebSocket-клиент не блокирует финализацию: ограниченные очереди/таймауты, прогресс можно
   объединять, терминальный статус восстанавливается через snapshot/API.
6. После reconnect UI сначала синхронизирует состояние; доставка допускает повтор.

Перед этим полезно закрыть остаток этапа 4, пункта 7: `job_view` и HTTP-слой читают `job["state"]`,
а не запись.
